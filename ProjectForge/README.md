# ServerProjectForge — 中央服务器 V 工程插件

## 目标与交付

这是原 VCPChat 工程施工核心的独立中央服务器版本，面向 Windows x64。操作全部通过 Agent 工具调用完成，不需要 Electron、VCPChat、页面、侧栏或 IPC。

- 操作插件：ServerProjectForge，入口为 [ServerProjectForge.js](ServerProjectForge.js)，清单为 [plugin-manifest.json](plugin-manifest.json)。
- 状态插件：ServerProjectForgeStatus，位于 [ProjectForgeStatus](../ProjectForgeStatus/plugin-manifest.json)，只读原子摘要，不启动第二个施工核心。
- 原 VCPChat 插件保持不动。中央版使用独立工具名，避免注册重名；**同一磁盘工程仍应只选择一个权威施工实例**。
- 原有 25 个命令保留，新增工作区管理及原 GUI 业务能力共 7 个命令，总计 32 个。
- 核心账本、写锁和歧义票据常驻；不把核心改成每次启动的同步脚本，不新增 HTTP 操作接口。

## 安装与启用

1. 将本目录和相邻的 [ProjectForgeStatus](../ProjectForgeStatus/plugin-manifest.json) 一起保留在中央服务器插件目录中。
2. 使用 Windows x64、Node 22.13 以上版本，推荐仍受支持的 Node LTS。进入本插件目录执行 npm ci。生产环境可执行 npm ci --omit=dev。不要只依赖中央根目录中的依赖：插件固定了独立的解析和校验依赖版本。
3. 编辑 [config.env](config.env)。必须配置管理员允许根目录，例如将 [授权根配置](config.env:6) 设置为 JSON 字符串数组，内容示例为两个绝对路径 D:/AgentWorkspaces 和 E:/Projects。Windows 路径建议使用正斜杠。
4. 可选设置 [默认工作区](config.env:9)，目录必须已存在且位于允许根内；留空时由 Agent 登记。
5. 重启中央服务。修改常驻插件配置后应重启，不依赖清单元数据热更新来重建运行时。
6. 给需要施工的 Agent 添加工具说明占位符：{{VCPServerProjectForge}}。
7. 需要状态感知时再添加：{{VCPServerProjectForgeStatus}}。这与工具说明是两个不同占位符。

**空授权根表示不授权，不是允许全盘。** 本次交付未替用户选择真实施工目录，默认执行开关关闭。

## 工作区与权限

管理员授权根是最大边界，Agent 只能在其中登记工作区，不能通过命令扩大允许根范围。

- [RegisterWorkspace](ServerProjectForge.js:118)：提供别名和已存在目录，创建稳定工作区 ID。
- [SetWorkspaceEnabled](ServerProjectForge.js:118)：启用或停用；必须显式提供布尔开关。停用后既有工程只读。
- [SetActiveWorkspace](ServerProjectForge.js:118)：切换后续创建工程使用的默认工作区。
- [ListWorkspaces](ProjectForgeService.js:412)：查看别名、ID、目录和启用状态。

工作区注册表保存在独立数据目录。工程记录仍保留稳定工作区 ID、相对子路径与原始根目录。旧工作区 ID 找不到时可以按已记录根目录解析，但写入仍须通过当前工作区授权。

登记工作区不得包含插件自身、插件状态组件、数据库、恢复目录或状态摘要；这些位置也不能成为施工目标。请把工作代码放在服务器程序和内部数据之外。

目录越界使用词法路径和真实路径共同校验，覆盖 Windows junction、符号链接、父目录未创建的目标、设备路径、ADS 和保留设备名。此校验不是内核沙箱；恶意本地进程的并发路径替换、硬链接和具有同等账户权限的程序仍须通过 Windows ACL、独立服务账户和部署隔离控制。

## Agent 调用示例

以下是协议文本，不是命令行。

### 登记工作区

```text
<<<[TOOL_REQUEST]>>>
tool_name:「始」ServerProjectForge「末」,
command:「始」RegisterWorkspace「末」,
alias:「始」demo「末」,
path:「始」D:/AgentWorkspaces/demo「末」
<<<[END_TOOL_REQUEST]>>>
```

### 创建工程

```text
<<<[TOOL_REQUEST]>>>
maid:「始」Kerr「末」,
tool_name:「始」ServerProjectForge「末」,
command:「始」CreateProject「末」,
name:「始」登录模块重构「末」,
workspace:「始」demo「末」,
dir:「始」application「末」,
todos:「始」阅读现有实现
修改校验逻辑
运行测试并提交报告「末」
<<<[END_TOOL_REQUEST]>>>
```

后续使用返回的工程 ID。所有文件路径相对该工程根目录；不要把本机客户端路径当作中央服务器路径。

### 推荐施工流程

1. 工作区查询或登记 → 创建或查询工程 → 更新待办。
2. 符号查找 → 按符号读取 → 通过符号、行号或文本锚定编辑。
3. 写操作填写原因与操作者署名；可关联待办序号。
4. 遇到歧义时保留票据并二轮选择，不猜测命中位置。
5. 检查差异、代码诊断；使用可信函数试跑或中央已有终端工具验证。
6. 提交报告；需要独立验收时由评审 Agent 执行保留原报告的验收命令。
7. 回退前先预演，出现外部改动时不自动强制覆盖。

完整原有参数、批量编辑串、符号寻址和示例见 [插件清单](plugin-manifest.json)。

## 原 GUI 业务能力的 Agent 接口

不迁移 UI，但保留以下业务能力：

| 命令 | 行为 |
|---|---|
| GetBatch | 工程 ID 和批次引用，返回批次及节点 |
| GetNode | 工程 ID 和节点引用，返回前后文本、大小、截断标记、后续变更数 |
| RevertFileChange | 对单个节点恢复到之前或之后；要求操作者署名，可预演、确认冲突，生成新回退批次 |
| AcceptProject | 只接受待验收工程，保留原报告及作者，追加验收署名；重复调用幂等 |

这些命令由 [中央分发器](ServerProjectForge.js:118) 适配既有业务层，没有开放 GUI 或网络路由。

单文件回退应先预演，再把预演返回的文件哈希带回执行；预演时不存在的文件可使用 missing 表示。预演后文件又发生变化，即使确认冲突也拒绝覆盖。节点内容预览每侧最多 32000 字符，长文件应按行或符号继续读取。

## 数据、恢复与并发

默认数据在中央根目录下独立的工程数据目录，具体配置见 [config.env](config.env:13)。

- 数据库：SQLite WAL，完整快照以内容哈希寻址并压缩；不是仅保存差异。
- 注册表：工作区状态原子保存。
- 票据：保留原先 30 分钟内存票据语义，重启失效，不伪装为跨重启持久任务。
- 并发：中央入口全部调用排队，防止不同工程 ID 指向同一个物理文件时交错修改。当前优先正确性，不承诺跨工程高并行。
- 单实例：数据目录和数据库分别加进程间锁；锁心跳丢失时依赖锁库的失效处理。不要用不同数据库实例同时施工同一目录。
- 写入：通过 [恢复日志模块](mutationJournal.js:39) 保存写前映像，落盘后在 SQLite 事务中记录提交标记；记录失败时补偿文件变更。
- 启动及调用前恢复：处理未完成恢复日志。已提交日志只清理，不撤销已提交内容；外部漂移或部分写入无法安全识别时保留日志并拒绝继续，不覆盖未知内容。
- 删除：先存数据库快照，再移动到 Windows 回收站，关闭库的路径通配解释。回收失败不会静默改用硬删除。
- 多文件删除保留原先逐文件回执语义：可能部分成功，失败列表必须检查，不把它描述成全批事务。
- 日志和快照包含代码，应限制数据目录的账户访问权限。

进程被强制结束或硬盘断电时，数据库与文件系统不能构成真正的跨资源事务。恢复日志帮助识别和恢复中断；出现冲突必须人工核查，不能宣称任何故障都可以自动无损恢复。

## 可信函数试跑和 Trace

[执行开关](config.env:20) 默认关闭。管理员显式启用后，才允许函数试跑，并允许 Trace 在受限子进程中加载工程的 preload 声明表；关闭时 Trace 仍有字面量 AST 事实，但不执行工程声明代码，声明式 API 信息会缺失。

试跑支持原有 JS/CJS/ESM、Python 和 Rust 既有标准测试。保持以下事实：

- 函数返回不代表测试通过；零测试、忽略测试不算通过。
- Rust 依赖本机 Cargo 和离线可用依赖；没有工具链时明确报告环境错误。
- 模块导入、准备代码、工程配置的运行时、Cargo 构建脚本与被测程序都可以写盘联网。
- 子进程环境仅传递运行时发现和操作系统必需项，不默认继承中央 API 密钥；但这不是安全沙箱。
- 总超时、有界日志、结果体积上限、取消信号和 Windows 进程树终止保留。
- 执行副作用不自动进入施工快照。返回的源码哈希不是依赖闭包指纹。

## 静态折叠状态

详见 [状态插件配置](../ProjectForgeStatus/config.env)。

核心每次工具调用后及定时心跳原子发布近期最多 20 个仍可写工程的有界摘要；静态插件每 30 秒读取：

- 零阈值：一行概况，包含更新时间。
- 中相关：近期工程状态及待办完成比例。
- 高相关：上述信息与每个工程最多五项未完成待办。
- 过期、核心关闭、空库、文件损坏时返回短兜底，不把旧数据当实时结果。

默认不发布源码、完整报告、访问凭据或绝对目录。工程名、待办标题仍是工作数据，不能填写密钥；它们不是系统指令。摘要是全局静态状态，不提供按 Agent 身份隔离；敏感环境应关闭该占位符或配置全局工程筛选。

修改核心数据目录或摘要路径时，必须同步修改静态插件的共享摘要路径，否则静态插件会正确显示“无摘要”而不是自动寻找任意数据库。

## 与中央已有工具协作

中央文件工具和 PowerShell/终端插件继续独立使用，不重复建设终端、Git 或外部 CLI 调度器。

- 工程内受审计的修改优先走本插件。
- 通用文件下载、目录浏览等可用中央文件工具。
- 构建、测试、Git、外部编程 CLI 可用中央已有终端工具。
- 其他工具修改文件属于外部漂移：后续工程操作或回退会检测，但不会自动为此前全部外部修改创建可靠的施工事务。
- 不应让两个工具并发修改同一文件；不要把操作者署名当作身份鉴权。

## 旧工程数据迁移

1. 停止旧分布式工程实例和中央新实例，先备份旧数据库及工作代码。
2. 关闭数据库后再复制。若不能保证 WAL 已检查点落盘，应使用 SQLite 备份接口，或一致地保存数据库及其 WAL/SHM；不要只复制一个运行中的数据库主文件。
3. 将副本配置为中央版数据库路径；启动时保留既有补列迁移。
4. 在中央授权根中登记对应工作目录。旧工作区 ID 可以不一致，原记录根目录必须仍在当前授权工作区内；目录已搬迁时需由管理员先核对根映射，不能直接放宽到全盘。
5. 查询工程、历史及只读差异，先做回退预演，再允许实际施工。
6. 内存票据不能迁入；需要重新提交歧义编辑。
7. 不合并两个不同施工账本，不宣称数据库复制等于远程文件同步。

## 开发与验证

- 在本插件目录执行 npm test，运行 Windows 裸 Node 回归。
- 执行 npm run build:indexer 使用 [构建入口](indexer/build-runtime.js:33) 重建本机索引器，需要 Rust 1.89 及相应 C 构建工具链；重建前停止中央实例以释放运行中的可执行文件。
- 提供 Windows x64 预编译运行时；缺失或协议不匹配时符号类能力明确降级，行号/文本编辑仍可用，不伪造 AST 结果。
- [中央宿主测试](tests/central-host.test.js:10) 执行真实中央加载器与调用桥，但隔离审批、日志、知识库等无关服务，并只发现这两个插件；它不等于启动整套生产服务器。
- [恢复故障注入](tests/mutation-journal.test.js:28)、[文档读取](tests/document-reader.test.js:26)、[后端权限与关闭](tests/server-backend.test.js:24) 以及迁入的 AST、Trace、编辑、历史测试共同验收。
- PDF、Word、Excel 和 CSV 已适配独立依赖；旧式 Excel 二进制格式明确不支持，需先转换。
- 本机无 Cargo 的 Rust 实际编译运行用例会明确跳过，不记为通过；预编译索引器的 Rust AST 与宏提取可独立验证。
